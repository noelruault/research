# Lessons — 1brc

Durable, cycle-to-cycle. Read first, obey. One tight bullet each; no one-off noise.

- Gate for `1brc/code/gen`: `cd 1brc/code/gen && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test ./...`. The `test -z` matters: `gofmt -l` exits 0 even when it lists unformatted files, so `gofmt -l . && ...` silently passes.
- Tracked files cannot be written from the shell here (a `bash-write-guard` PreToolUse hook blocks heredocs and `sed -i` on anything git-tracked). Use Edit/Write for tracked files; shell heredocs only work for files not yet committed. A `comment-verbosity` hook also rejects comment blocks over ~3 lines, and a formatter hook reflows comments to one sentence per line after every edit.
- Two of the 413 official station names contain a comma (`Washington, D.C.`, `Flores,  Petén`) and the output separator is `", "`. Never split the result line on `", "` to compare or count entries; byte-compare against `1brc/testdata/expected-*.out`, and count entries with `tr -cd '=' | wc -c`.
- A decimal that looks like a rounding tie usually is not. `-0.05` and `-0.1/2` both sit just below the tie in float64, so they round to `-0.1`, not `-0.0`. Two test expectations were wrong on this before the code was. When a mean is off by one tenth, suspect the float64 representation of the tie before suspecting the rounding rule.
- Label performance and numeric claims before writing them into a comment, and measure the cheap ones. A "float64 drifts ~1e-2" justification in `tenths.go` was wrong by four orders of magnitude; a 15-line test settled it in one run. The worst-case bound `n·eps·sum` is not the behaviour — summation error cancels like `sqrt(n)·eps·sum`.
- `openssl dgst -sha256` hashes the 13.8 GB file in ~6 s (hardware SHA); `shasum -a 256` is roughly 20x slower. Use openssl for anything over a gigabyte.
- Generation is ~725 MB/s single-threaded (1b rows in 18 s), so do not reach for a parallel generator. Regenerating any file is cheap; the seed and command in `02-baseline-data.txt` reproduce every one byte-for-byte.
- No JDK on this machine (Java 8 JRE, no `javac`), so upstream's Java cannot be run and output semantics are derived from its source. If a correctness question turns on what the JVM actually does, install a JDK 21+ first rather than reasoning about it.
- Mutation-test every new test before calling a group reviewed, and mutate the thing the cycle just *decided*, not only the obvious arithmetic. Two cycles running, the surviving mutant was a semantic choice made deliberately earlier in the same cycle (here: first-`;` vs last-`;`, matching `gen.Aggregate`) and left with no test on it. A byte-compare against clean 10m data cannot catch it, because the divergence only shows on input the clean data never contains.
- On this machine the page cache LOSES for files larger than ~half of RAM: 15 parallel `pread`s of 1 MiB with darwin `F_NOCACHE` (`fcntl(fd, 48, 1)`) read the 13.8 GB file in 754 ms against 1.126 s page-cached, and mmap needs 6.7 s because 16 KiB pages mean 842k faults on a path that does not parallelise. Measure the I/O strategy before porting one from a Linux write-up. Cold-cache numbers are not available at all (`purge` needs sudo, this loop is unattended) — use `F_NOCACHE` and label it "uncached", never "cold".
- Check `pmset -g batt` BEFORE benchmarking, not after. This machine has been on battery for whole measurement sessions, which `spec.md:42` makes provisional, and re-measuring costs the whole cycle's benchmark time. `1brc/scripts/bench.sh` now records power and load and stamps PROVISIONAL itself.
- If a rebase happens mid-cycle (the operator pushes while a group is being built), re-point EVERY sha already written into built.md, handoff.md, review.md and any data companion: the rebase orphans them and the ledger ends up citing commits that no longer exist on the branch. Record the ledger shas AFTER the last rebase, or grep for the old ones before pushing.
- A new kernel is not checked by agreeing with the corpus; it is checked by agreeing with the OTHER kernels on input the corpus cannot express. The first-vs-last-`;` divergence has now shipped three times, most recently in `TokenizeBatch`, where every agreement test passed because no key set produces a name containing `;`. Any new code that splits a row gets a `;`-in-name case against a sibling implementation before it ships. The same "no corpus can express it" rule applies to the report: before pushing, grep every "measured" sentence for its raw output in the data companion — this cycle published a control run, a `PARKED.md` and an H6 margin that existed in no committed file.
- A verdict from the 100m file is worthless: measured across seven strategy arms, SEVEN disagreed with the 1b file - four inverted (parse, buffer size, table size, F_NOCACHE) and three vanished into overlapping ranges (mmap is 5.6x slower at 1b and marginally FASTER at 100m). At 1.4 GB nothing is I/O bound; at 13.8 GB, 53.5% of RAM, everything is. Iterate on 100m, decide on 1b. The same trap has a correctness twin: splitting work on raw byte offsets has at least four distinct off-by-one traps (a range starting exactly ON a row boundary, a range shorter than one row, a buffer no larger than its range, and the first-`;`-versus-first-`\n` question), and a sweep of worker count x buffer size x split x reader against the reference is what finds all of them - a single-configuration test finds none.
- A microbenchmark's delta only transfers if its BASELINE is the shape production runs. `04-asm-kernels.md` measured the batch tokenizer at −40.4% and `go-v2-kernels` measured it at +10.4% end-to-end, a 50-point swing, because the microbench's baseline was a single-needle staged tokenizer writing a token stream and the binary's real arm is a dual-needle scan consuming the row in place. Before quoting a kernel delta forward, name the baseline it was measured against and check that the binary contains it. This is E-09's twin: E-09 says a 10x-smaller file does not rank arms, E-11 says a differently-shaped baseline does not either.
- A guard can survive mutation because a SIBLING guard masks it, and then neither is pinned. Here `pendingSep < 0` and `pendingSep+next != end` each caught the other's mutant, so both looked tested and neither was. Delete the redundant one and re-mutate: the survivor tells you which check is load-bearing. A test that only asserts "an error came back" will hide this every time — assert the failure MODE (this one now panics on the mutant) or place the bad input where only the guard under test can catch it.
- Before writing "no earlier report records X" into a report, grep for X. This cycle published that the Super/Performance core split was unrecorded; three reports record it, one of them the definition. Novelty claims are the cheapest thing in a report to check and the most embarrassing to get wrong, and they are never load-bearing — the finding survives without them.
- Arithmetic written in prose is never re-derived by anyone, so evaluate every derived figure in a shell or `python3 -c` line and paste the output. Three shipped wrong in one cycle and none of them was measured: a cost formula, its own worked example, and a count of ledger rows that `grep -o 'Verdict: [A-Za-z-]*' | sort | uniq -c` settles in one run. The 10k key set is the standing trap of this kind: its rows are **57.09 bytes** against the official set's 13.80 (from the recorded size of `measurements-10k-stations-10m.txt`), so "the same experiment with more stations" at 1b rows is a 57 GB file at 2.22x RAM, not a 13.8 GB one — hold BYTES constant, 241.6M rows, if the point is to reproduce the 1b file's memory regime.
