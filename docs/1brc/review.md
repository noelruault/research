- reviewed def-understand 4145227 + env-data d22e3dc: REPAIRED — four defects found by auditing the diff against the handoff. (1) `AppendTenths` assumed the whole part fitted in two digits and silently emitted garbage above it (`1000` tenths printed as `":0.0"`), while `ParseTenths` happily accepted `"500.0"`; replaced with `strconv.AppendInt` (also shorter) and added `TestAppendTenthsBeyondLegalRange`. (2) `Aggregate` accepted out-of-range temperatures and folded them into a plausible-looking result; it now fails with the line number, pinned by `TestAggregateRejectsOutOfRangeTemperatures`. (3) The `Tenths` doc comment justified the whole integer-grid design with a *derived* claim — "float64 drifts by ~1e-2 per station" — that measurement disproved by four orders of magnitude (actual drift 9.2e-07, and float64 recovers the exact sum). The design is right, the stated reason was not; the comment now cites `TestFloat64AccumulationDriftIsSmall`, which measures it. (4) `01-definition.md` cited `semantics_probe_test.go`, a file that does not exist (it is `tenths_test.go`) — a claim-vs-diff mismatch found exactly where the handoff protocol says to look. Also closed a contract gap the group created: `1brc/code/gen` had no green gate in `spec.md`, so the new code was ungated; added one, with `test -z "$(gofmt -l .)"` because `gofmt -l` exits 0 even when it lists files. Mutation-tested the suite over 17 mutants across both files: all 17 caught after the fixes, and the one survivor in the first round (a separator-less line that is itself a valid temperature, which panics if the check is removed) is now covered. Expected outputs re-derived after every fix and confirmed byte-identical, so none of the repairs moved the correctness target.

- reviewed asm-kernels b4be167 (repairs 730d166, 0956159): REPAIRED — five defects, one of them a correctness bug in the kernel the report recommends. (1) `TokenizeBatch` ended a name at the LAST `;` in a row while `TokenizeScalar`, `TokenizeStagedSWAR` and `TokenizeStagedNEON` all end it at the first, which is `gen.Aggregate`'s rule: on `Ab;cd;1.0` it reported a 5-byte name against the others' 2-byte one, so it would have attributed the row to a different station. Neither key set produces a name containing `;`, so `TestTokenizersMatchTheScalarReference` and `TestBatchBenchLoopCoversEveryRow` both passed over both corpora with the bug present — the benchmark was pricing a kernel that was not doing the job correctly. This is the THIRD appearance of the first-vs-last-`;` divergence in this study (lessons.md records it in `go-skeleton`, one group earlier). Fixed with a one-line guard plus `TestEveryKernelEndsTheNameAtTheFIRSTSemicolon`, mutation-tested: reverting the guard fails the new test while every pre-existing test still passes, which is exactly the gap. The test asserts only the name BOUNDARY, because a `;` in a name makes that row's temperature unparseable by construction and the kernels then resynchronise differently by design (staged from the parse's output, batch from the newline mask). (2) The repair changed the kernel the largest published number measures, so it was re-measured: `-42.3%` becomes `-40.4%` and `-40.7%` across two post-fix runs, corrected at all six sites that published it (report x4, data companion, built.md, handoff.md) with `CORRECTIONS.md` C3 recording the superseded claim. Both post-fix runs are published because they disagree about the 10k pair's separation and quoting only the agreeing one would be choosing the answer; the 10k crossover is now stated as a direction that reproduced twice, not a separated margin. (3) The report's Method section published H6 margins of `0.604` and `0.133 ns/row` while its own table and the data companion give `0.513` and `0.165` — a cross-invocation mix its own methodology forbids (`0.604` does turn up, in a different run). Corrected, and the "clears the floor by 60x to 600x" that followed from the wrong pair is now 83x to 513x, derived from the published floor. (4) The report claimed run-to-run spreads of "1-3%" as the reason its orderings are safe; measured full-range spread is 0.8% to 15.6%, and the noisiest loop of the eighteen is `batch/413`, the one the largest headline rests on. Replaced with the check that is both true and stronger: every verdict-bearing pair is disjoint over its ten runs, the winner's slowest beating the loser's fastest, with the one exception labelled. (5) The report cited a control run and a `PARKED.md` that existed in neither the repo nor any committed file. The control benchmarks were uncommitted; they are now committed, re-run, and their raw output is in the data companion, where the byte-identical twins agree to 0.001-0.002 ns/row. `1brc/PARKED.md` is created with P-01 (per-row NEON scan) and P-02 (NEON parse, never built, parked on a bound and recorded as a bound), all seven fields each, and indexed in root `PARKED.md`. Also verified rather than assumed: the page-guard test's claim that it catches a weakened over-read guard — narrowing the 16-byte guard to 8 makes `TestNEONIndexSemicolonStopsAtTheSliceEnd` segfault, as advertised.
