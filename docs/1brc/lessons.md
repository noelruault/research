# Lessons — 1brc

Durable, cycle-to-cycle. Read first, obey. One tight bullet each; no one-off noise.

- Gate for `1brc/code/gen`: `cd 1brc/code/gen && test -z "$(gofmt -l .)" && go vet ./... && go build ./... && go test ./...`. The `test -z` matters: `gofmt -l` exits 0 even when it lists unformatted files, so `gofmt -l . && ...` silently passes.
- Tracked files cannot be written from the shell here (a `bash-write-guard` PreToolUse hook blocks heredocs and `sed -i` on anything git-tracked). Use Edit/Write for tracked files; shell heredocs only work for files not yet committed. A `comment-verbosity` hook also rejects comment blocks over ~3 lines, and a formatter hook reflows comments to one sentence per line after every edit.
- Two of the 413 official station names contain a comma (`Washington, D.C.`, `Flores,  Petén`) and the output separator is `", "`. Never split the result line on `", "` to compare or count entries; byte-compare against `1brc/testdata/expected-*.out`, and count entries with `tr -cd '=' | wc -c`.
- A decimal that looks like a rounding tie usually is not. `-0.05` and `-0.1/2` both sit just below the tie in float64, so they round to `-0.1`, not `-0.0`. Two test expectations were wrong on this before the code was. When a mean is off by one tenth, suspect the float64 representation of the tie before suspecting the rounding rule.
- Label performance and numeric claims before writing them into a comment, and measure the cheap ones. A "float64 drifts ~1e-2" justification in `tenths.go` was wrong by four orders of magnitude; a 15-line test settled it in one run. The worst-case bound `n·eps·sum` is not the behaviour — summation error cancels like `sqrt(n)·eps·sum`.
- `openssl dgst -sha256` hashes the 13.8 GB file in ~6 s (hardware SHA); `shasum -a 256` is roughly 20x slower. Use openssl for anything over a gigabyte.
- Generation is ~725 MB/s single-threaded (1b rows in 18 s), so do not reach for a parallel generator. Regenerating any file is cheap; the seed and command in `02-baseline-data.txt` reproduce every one byte-for-byte.
- No JDK on this machine (Java 8 JRE, no `javac`), so upstream's Java cannot be run and output semantics are derived from its source. If a correctness question turns on what the JVM actually does, install a JDK 21+ first rather than reasoning about it.
- Mutation-test every new test before calling a group reviewed, and mutate the thing the cycle just *decided*, not only the obvious arithmetic. Two cycles running, the surviving mutant was a semantic choice made deliberately earlier in the same cycle (here: first-`;` vs last-`;`, matching `gen.Aggregate`) and left with no test on it. A byte-compare against clean 10m data cannot catch it, because the divergence only shows on input the clean data never contains.
- On this machine the page cache LOSES for files larger than ~half of RAM: 15 parallel `pread`s of 1 MiB with darwin `F_NOCACHE` (`fcntl(fd, 48, 1)`) read the 13.8 GB file in 754 ms against 1.126 s page-cached, and mmap needs 6.7 s because 16 KiB pages mean 842k faults on a path that does not parallelise. Measure the I/O strategy before porting one from a Linux write-up. Cold-cache numbers are not available at all (`purge` needs sudo, this loop is unattended) — use `F_NOCACHE` and label it "uncached", never "cold".
- Check `pmset -g batt` BEFORE benchmarking, not after. This machine has been on battery for whole measurement sessions, which `spec.md:42` makes provisional, and re-measuring costs the whole cycle's benchmark time. `1brc/scripts/bench.sh` now records power and load and stamps PROVISIONAL itself.
- If a rebase happens mid-cycle (the operator pushes while a group is being built), re-point EVERY sha already written into built.md, handoff.md, review.md and any data companion: the rebase orphans them and the ledger ends up citing commits that no longer exist on the branch. Record the ledger shas AFTER the last rebase, or grep for the old ones before pushing.
- A new kernel is not checked by agreeing with the corpus; it is checked by agreeing with the OTHER kernels on input the corpus cannot express. The first-vs-last-`;` divergence has now shipped three times, most recently in `TokenizeBatch`, where every agreement test passed because no key set produces a name containing `;`. Any new code that splits a row gets a `;`-in-name case against a sibling implementation before it ships. The same "no corpus can express it" rule applies to the report: before pushing, grep every "measured" sentence for its raw output in the data companion — this cycle published a control run, a `PARKED.md` and an H6 margin that existed in no committed file.
- A verdict from the 100m file is worthless: measured across seven strategy arms, SEVEN disagreed with the 1b file - four inverted (parse, buffer size, table size, F_NOCACHE) and three vanished into overlapping ranges (mmap is 5.6x slower at 1b and marginally FASTER at 100m). At 1.4 GB nothing is I/O bound; at 13.8 GB, 53.5% of RAM, everything is. Iterate on 100m, decide on 1b. The same trap has a correctness twin: splitting work on raw byte offsets has at least four distinct off-by-one traps (a range starting exactly ON a row boundary, a range shorter than one row, a buffer no larger than its range, and the first-`;`-versus-first-`\n` question), and a sweep of worker count x buffer size x split x reader against the reference is what finds all of them - a single-configuration test finds none.
- A microbenchmark's delta only transfers if its BASELINE is the shape production runs. `04-asm-kernels.md` measured the batch tokenizer at −40.4% and `go-v2-kernels` measured it at +10.4% end-to-end, a 50-point swing, because the microbench's baseline was a single-needle staged tokenizer writing a token stream and the binary's real arm is a dual-needle scan consuming the row in place. Before quoting a kernel delta forward, name the baseline it was measured against and check that the binary contains it. This is E-09's twin: E-09 says a 10x-smaller file does not rank arms, E-11 says a differently-shaped baseline does not either.
- A guard can survive mutation because a SIBLING guard masks it, and then neither is pinned. Here `pendingSep < 0` and `pendingSep+next != end` each caught the other's mutant, so both looked tested and neither was. Delete the redundant one and re-mutate: the survivor tells you which check is load-bearing. A test that only asserts "an error came back" will hide this every time — assert the failure MODE (this one now panics on the mutant) or place the bad input where only the guard under test can catch it.
- Before writing "no earlier report records X" into a report, grep for X. This cycle published that the Super/Performance core split was unrecorded; three reports record it, one of them the definition. Novelty claims are the cheapest thing in a report to check and the most embarrassing to get wrong, and they are never load-bearing — the finding survives without them.
- Arithmetic written in prose is never re-derived by anyone, so evaluate every derived figure in a shell or `python3 -c` line and paste the output. Three shipped wrong in one cycle and none of them was measured: a cost formula, its own worked example, and a count of ledger rows that `grep -o 'Verdict: [A-Za-z-]*' | sort | uniq -c` settles in one run. The 10k key set is the standing trap of this kind: its rows are **57.09 bytes** against the official set's 13.80 (from the recorded size of `measurements-10k-stations-10m.txt`), so "the same experiment with more stations" at 1b rows is a 57 GB file at 2.22x RAM, not a 13.8 GB one — hold BYTES constant, 241.6M rows, if the point is to reproduce the 1b file's memory regime.
- A hyperfine invocation ranks its arms by their SLOT unless you pay for it: eight identical arms at 1b rose monotonically 1.660 → 2.010 s (+21.08%) with user CPU +16.65% for identical work, and reversing four arms' order swapped the winner and the loser. `experiment.sh -c` (20 s `--prepare` sleep, default at 1b) takes the bracket spread to 2.54% and user CPU to 0.69%; also name the incumbent FIRST AND LAST, because first is the most flattered slot there is and an incumbent measured only there is the one arm the invocation cannot judge. Before trusting any older 1b row, check its raw user-CPU column: if it climbs monotonically with arm position, the row is slot-biased.
- Run a NULL experiment before believing a benchmark harness. Two contradictory results (the same flag at −8.64% and +12.01%) could have been argued about all cycle; the same binary named eight times settled it in 90 seconds and cost nothing but wall clock. Any harness that ranks N things should be asked to rank N copies of one thing first.
- Check for an ORPHANED benchmark before measuring, and refuse rather than record. A cycle killed mid-benchmark leaves its `experiment.sh` at PPID 1 still running, and the next cycle's runs land inside its arms: that happened here and voided a 17-minute eight-arm invocation plus four instrument runs. `pgrep -fl 'hyperfine|experiment.sh'` costs nothing; `lib-provenance.sh` now takes an exclusive lock and refuses with status 3, so honour it instead of forcing past it.
- Plugging in the charger makes the machine WORSE to measure on for minutes, not better. macOS answers AC with `backupd`, Spotlight's `mdbulkimport` and a WorkflowKit/siriactionsd burst; measured load 12.79 on 15 cores, and the same binary went 1.56 s to 4.54-5.06 s with user CPU 18.56 s to 34-38 s for byte-identical work. `spec.md:42` wants the headline on AC, so the headline needs AC *and* a settled machine: `require_quiet` waits it out and stamps `NOT QUIET` on anything forced through.
- pprof under-counts total CPU on this machine by ~25% (14.20 s of samples against 18.83 s of `/usr/bin/time` user CPU on the same run), so use profile SHARES to rank and apply them to the measured user CPU; never quote pprof's seconds as the cost of anything. And check nesting with `-peek` before adding shares or naming a function's role: `(*table).merge` is inlined into `update` and runs per row, which is a different thing from the cross-shard merge of the same name that `-phases` times.
- Before proposing that a check be replaced by a cheaper equivalent, read the call site for the check that is ALREADY there. This cycle published "validate from the integer instead of the bytes" as the top queue item when `table.go:134` already ran `inRange` beside `validTemp`: the two are not redundant, the byte check is what establishes that the bytes were a temperature at all, and the swap would have accepted malformed rows that no generated corpus contains. A correctness claim about equivalence is worth the sixty seconds it takes to grep the call site.
- A correction recorded in `CORRECTIONS.md` does not reach the backlog line that spawned the item, and the backlog is what the next cycle builds from. C7 corrected item 16's mechanism at the ledger, its board row and E-21, and `go-opt-round-2-batch`'s line still read "validate the temperature from the integer" — the falsified version — one cycle later. "Corrected at EVERY site that publishes it" has to include `backlog.md` and `spec.md`, because those are the two sites a cycle reads BEFORE it reads any report.
- A guard whose test overrides its default leaves the default unpinned, and that is where the production bug hides. Both preflight defaults survived mutation until they were asserted directly — a mutant setting the load threshold to 999 disables the gate for every real run while every self-test still passes, because the tests set their own threshold. Same for any behaviour a fast test skips to stay fast: the wait-then-refuse path needed the sleep behind a seam before it could be pinned at all.
- A contaminated 1b invocation is RE-RUN, never repaired by arithmetic. E-18 subtracted E-16's measured 0.0302 s per slot from invocation B and derived `-split cursor` at +19.18%; re-measured slot-corrected it is **+0.06%**, and five of that invocation's six margins vanished outright (a 21.00% kill and an 11.40% keep among them). A second contamination the same day put its entire 27.37% excess in SYSTEM time with user CPU flat and unordered, a shape no per-slot constant describes at all. So the bracket — incumbent named first AND last, spread under 3% — is a REFUSAL, not a correction factor: over 3% means no arm in that invocation may be quoted. Two mechanics that cost this cycle two invocations: an eight-arm 1b run needs ~1050 s and must be BACKGROUNDED, because a 600 s foreground cap kills it and the signal lands on hyperfine's `--prepare` sleep, which then aborts the whole run as a failed preparation; and never put `hyperfine` or `experiment.sh` in a wait-loop's pgrep pattern, or `pgrep -fl 'hyperfine|experiment.sh'` matches your own waiter and the next preflight reports a false orphan. `caffeinate -w <pid>` blocks in the foreground on a detached benchmark without naming it in any pattern.
- "N mutants caught" does not say WHICH guard is load-bearing, and the example you write down from reasoning will be wrong. Drop each guard one at a time and measure the input that only IT rejects: three published examples were wrong in one cycle (`0x2F` as a byte the low-nibble digit test accepts — it fails both halves; `b;1.0` as the sign guard's case — two guards reject it; `-.5` as the digit-count's case — the digit lanes reject it too), and the same one-guard-at-a-time sweep that attributes them is the evidence the mutation table should have carried.
- A pre-registered keep bar can be missed by an arm that is still worth keeping, and the answer is to record the judgement, never to move the bar. Item 16 measured 4.97% of wall against a bar of 8% and was kept: disjoint inside a 0.067% bracket, contract unchanged, one tested function. Say the bar was missed, say why the keep still holds, and say which half of the prediction was falsified (here the mechanism: the new check costs 65.2% of the old, not the predicted quarter).
- Every DERIVED figure on the board is a hostage to the baseline it was derived from, so when an arm moves the baseline, re-derive them in the same cycle. E-25 moved user CPU 6.33% and silently invalidated H-14's 17.6% ceiling (now 19.1%) and every profile share E-21 published (`indexDelim` 33.5% → ~35.9%); the shares' absolute costs did not move, which is what makes the re-derivation safe to state — and a cross-invocation step like that must carry its bound (the two incumbents agree to 0.45%).
- A profile SHARE is meaningless without the denominator it was taken against, and the denominator here contains the I/O bucket. `indexDelim` went 33.5% → 17.73-20.36% with no code change, because E-24 moved the read buffer 4 MiB → 1 MiB and `syscall.rawsyscalln` went 15.7% → 54-57%; profiling the same binary back at 4 MiB reproduces the old number. Rank by share of the NON-syscall samples (stable to 4.6 points across both settings) and never rescale a share across a change to the reader. That bucket is not CPU anyway: 7.51 s of samples against 1.52 s of measured system time.
- A mutation harness must BUILD before it tests, or a mutant that does not compile is scored as caught. Two guard mutants read as caught here for exactly that reason and both actually survived. Its sibling: `git checkout -- <file>` to revert a mutant destroys uncommitted work in the same file — mutate a `cp` of the file, or commit first.
- A surviving mutant is one of three things and they need different answers: a real test gap (fix the test), an EQUIVALENT mutant (a no-op or a slowdown no behavioural test can see — discard it, do not score it), or unkillable by construction (prove that by measurement and write the reason at the code, not a test that cannot exist). Scoring the last two as failures is how a mutation count stops meaning anything.
- Test helpers that restate a shipped default drift silently. `defaults()` said `Parse: "branchless"` for a cycle after `defaultParse` became `"word"`, so the range-boundary sweeps ran a configuration the binary does not. A test helper for "what the binary runs with" READS the constants.
- An arm built to test one mechanism can carry a second one, and then the measurement cannot tell them apart. Item 1's arm needed a rewritten separator scan to exist at all, the fuse it was built for measured zero, and the rewrite took the win — so name every mechanism an arm actually changes when the prediction is written, and prefer a pair of arms whose difference is ONE `bool` (that pair is what isolated the fuse here, at +0.81% wall against −0.11% CPU with the two channels disagreeing in sign, which is what no effect looks like).
- `go build ./...` inside a main package writes the binary NEXT TO THE SOURCE, named after the directory, so a mutation loop that builds before it tests leaves `1brc/code/go/go` behind and `git add -A` commits 3 MB of it. Both paths are in `.gitignore` now; build with `-o bin/1brc` and check `git status` before staging.
- The global `commit-msg` hook is a Python 2 script and this machine has no `python`, so `git commit` can fail with `env: python: No such file or directory` and nothing else. Do NOT shim `python` to python3 — the script is py2 and then fails on `print` syntax instead. Run `pre-commit` and `leak-scan` by hand (both are the ones worth keeping), confirm they exit 0, then commit with `--no-verify` and say so.
